# The platform, as measured: snapDOM

This file holds what snapDOM, the optional second engine, does, and where it differs from HTML-in-canvas. It is part of [the platform measurements](../platform.md), which lists every item and the table conventions.

| # | What the platform does | Evidence |
|---|------|---------|
| <a id="item-22"></a>22 | **snapDOM freezes a compositor-only animation at whatever the first capture saw; HTML-in-canvas captures it live.** A descendant wearing an infinite `opacity` keyframe produced **0** paints over a 3s window under snapDOM and a pixel still at full opacity, while the same subtree under HTML-in-canvas produced **360** paints over the same window and sampled mid-fade. snapDOM has no change signal for it: nothing mutates, and an infinite animation fires `animationstart` once and `animationend` never. This is the tolerable outcome — the alternative is rasterizing the subtree forever — but it means decorative motion inside a snapDOM Surface is a still frame. A CSS *transition* is different — `transitionrun` and `transitionend` both signal — so a 400ms `transform` transition captured in **3** paints under snapDOM against **50** under HTML-in-canvas, both ending on the correct pixels. `repaint()` is the escape hatch for anything else. (measured 2026-09-10, Chrome 151, headless, dpr 1, snapDOM 3.0.0-beta.1) | 200×100 subtree, 50%-tall child on `@keyframes{from{opacity:1}to{opacity:0}} 2s linear infinite`: snapDOM `paintCount` delta **0/3000ms**, sample `[254,0,1,255]`; HTML-in-canvas delta **360/3000ms**, sample `[47,0,208,255]`. Transition leg, same subtree, `transform 400ms linear`: snapDOM 3 paints, HTML-in-canvas 50, end pixels `[0,0,255,255]` top / `[255,0,0,255]` bottom on both |
| <a id="item-23"></a>23 | **snapDOM reproduces flat CSS fills exactly, and a real page to within glyph antialiasing.** Worst per-channel error against the authored colors is 0/255 on both halves of a two-color subtree, the same number HTML-in-canvas scores. Against a browser screenshot of a real card, HTML-in-canvas is byte-identical (MAE 0.000, max 0) and snapDOM reaches the same on 6 of 9 cards, with a 31-64 pixel residual on two more that is one letter's antialiased edge. Item 25 is what the remaining engine-side difference was. (measured 2026-09-11, Chrome 151, headless, dpr 2, snapDOM 3.0.0-beta.1) | `npm run gate:capture-engines`: `fidelity 0/255` both engines. Flight's nine page-side cards at dpr 2, source canvas vs `page.screenshot` of the same element: native 0/323,420 px differ; snapDOM 0 on six cards, 64 and 31 on two, 10,120 on one (item 26) |
| <a id="item-24"></a>24 | **snapDOM drops BOTH of a form field's pseudo-elements, and warns about neither.** An `<input>`'s `::after` and its `::placeholder` are absent from the clone: an `appearance: none` checkbox's tick does not draw, and every `::placeholder` declaration — `text-transform`, `letter-spacing`, `font-size` — is lost, so the placeholder renders at the field's own type. Pseudo-elements elsewhere are fine: the same tick on a `<div>` draws. snapDOM stamps `data-snapdom-has-after` on the input and a `snapdom-ph-*` class and materializes neither. Shimmed by `packages/react/src/snapdomFieldPseudoElements.ts`. (measured 2026-09-11, Chrome 151, snapDOM 3.0.0-beta.1; same on 3.8.2, 2026-11-22) | five-case rig: `div::after`, `span::before` and `p::first-line` all render; `input:checked::after` and every `input::placeholder` property do not. Flight, before the shim: 787-806 of 323,420 px wrong on six of nine cards, all tick and placeholder; after, 0. On 3.8.2 without the shim `gate:capture-engines` fails: 7 of 3000 blocks differ, worst 190 |
| <a id="item-25"></a>25 | **snapDOM's `width`/`height` STRETCH the element to fill them; `drawElementImage` renders at the canvas's own ratio.** The two only agree while the element exactly fills its host. A 260px element in a 300px host, store 624x132, asked for the store's size: the native engine drew it in the leftmost 541px and left the rest clear, snapDOM stretched it across all 624. The consequence for a consumer: ask a rasterizer for `element box x per-axis scale`, never for the store, and blit the answer at its natural size. (measured 2026-09-11, Chrome 151, headless, snapDOM 3.0.0-beta.1) | same subtree, both engines, texture compared directly: at rest and at an unequal per-axis density the two are byte-identical (MAE 0.000); after a resize the density band absorbs, asking for one density and stretching gives MAE 78.9 with 37% of pixels differing, and asking for `box x scale` per axis gives MAE 0.418 with 0.74% |
| <a id="item-26"></a>26 | **A snapDOM capture can place a block 2px off where the browser does, and `reconcile: true` does not always catch it.** One Flight card of nine renders everything above its divider byte-identically and everything below it 2px low. The option is still worth setting — snapDOM warns `reconcile-risk` without it on any subtree holding inline or table-cell text, and it costs nothing measurable — but it is not a guarantee of layout parity. (measured 2026-09-11, Chrome 151, headless, dpr 2, snapDOM 3.0.0-beta.1) | card 8: 0 differing px above y=218, 10,120 below, unimproved by a ±4px whole-image shift (so not a uniform offset) and unchanged by `reconcile`. Capture cost with and without reconcile over nine cards: 8-21 ms either way |
| <a id="item-27"></a>27 | **A drag re-captures for reasons that are not content, and under a main-thread rasterizer each one is a whole panel.** Two of them, measured on a nine-card board over one grab-and-lift. The LOD ladder moves a Surface's raster supply every frame it moves, and the source took that as a reason to rasterize — but the backing store already carries its old raster across a re-cut, and both stores hold the same element box, so the difference is the density change alone and the band exists to spend exactly that. And the page-side copy a source holds is rebuilt on every mutation of the live content, where almost none of those rebuilds differ from the copy already in place. Dropping both took the drag from 65 captures to 40 and its blocking time from ~140 ms to ~115 ms. What remains is the engine's own cost, and it does not reach the native engine's zero. The settle is what pays the band back, and it has to watch the DENSITY as well as the box or a Surface that only moves in depth never asks for a sharp capture at all. A density a caller NAMES is not a ladder step and is not skipped: a scene that names one at a phase boundary is asking to arrive at that density (decisions.md #44). (measured 2026-09-11, Chrome 151, headless, dpr 1, snapDOM 3.0.0-beta.1) | Flight, 40-step drag of one card, `paintStats` delta and `longtask` total: snapDOM 65 captures / 135-147 ms / 2-3 frames over 33 ms before, 40 / 114-126 ms / 2 after; HTML-in-canvas 35-53 captures / 0 ms / 0 frames throughout. Page-side rebuilds during the drag: 41, of which 40 byte-identical to the copy in place. A settle that re-arms on density but rasterizes unconditionally costs 58 captures / ~200 ms; skipping the ones whose store is already the one the last raster was made for returns it to 40 |
| <a id="item-28"></a>28 | **An SVG loaded as an IMAGE lays its HTML out at one device pixel per CSS pixel, whatever resolution it is rasterized to. Inline, the same markup does not.** This is the whole of snapDOM's fidelity gap, and it is not snapDOM's doing: it serializes `border-top-width:1.5px` faithfully, and the value is lost when Chrome renders the SVG. An SVG image is laid out in an isolated document pinned to dpr 1, so at dpr 2 every half pixel the page resolves is quantized away — a `1.5px` border draws at `1px`, a rule on a half pixel lands a whole one off. The art still rasterizes crisply at the OUTPUT scale, which is why it reads as wrong weight and position rather than blur, and why no amount of output resolution recovers it. The quantization is universal — Chromium, Firefox and WebKit all do it — so no engine choice and no other library escapes it. Chrome alone exempts PAINTED properties, which is a Chrome detail and not a technique: Firefox quantizes a painted stroke too and WebKit does not draw one. snapDOM cannot avoid the image path — it is how arbitrary DOM reaches a canvas at all — so this is a ceiling for the engine and not a bug to fix in it. HTML-in-canvas never goes through an image and reproduces the fraction exactly. (measured 2026-09-11, Chrome 151, real GPU, dpr 2, snapDOM 3.0.0-beta.1) | Same SVG, same document, dpr 2: inline `<svg><foreignObject>` draws a `1.5px` border in **3** device rows; the identical markup as `<img src="data:image/svg+xml,...">` draws it in **2**. `border-width` ladder through the image path: 0.5 -> 1.0, 1 -> 1, **1.5 -> 1.0**, 2 -> 2, **2.5 -> 2.0**, 3 -> 3 CSS px, all crisp (pure 0/255), so it is a snap and not a resample. Rasterizing that image at 1x, 2x and 4x, and through a scaled `viewBox`, returns 1.0 every time. Painted equivalents at 1.5px, same path, Chrome: `box-shadow: inset` **3** rows, `linear-gradient` **3** rows, `outline` 2 (outline is laid out). The same `box-shadow` case across engines at dpr 2: Chromium **3** rows, Firefox **2**, WebKit **0** (not drawn); the `border` case is **2** rows in all three. Flight card 515x158 CSS at dpr 2, element screenshot against the raster with the placeholder shim installed: MAE 4.28, 13,552/325,480 px over 24; checkbox stroke browser 3 texels / snapDOM 2; rail `hr` browser rows 43-44 / snapDOM 44-45; divider browser 218 / snapDOM 218-219; note underline browser 284-285 / snapDOM 286+. Ink extents of the headline, body copy, checkbox box, `DONE` and `ADD NOTE` are identical in both. Rewriting the SVG to a doubled `foreignObject` whose content wears `zoom: 2` restores the stroke to 3 texels and then costs a texel on the whole foot row, for a net LOSS (MAE 4.54, 15,245 px) — `zoom` multiplies computed font sizes before layout, so it is not the same operation as a finer device grid. `gate:capture-engines` scores 0/1200 blocks at rest because its fixture carries no fractional-width border |
| <a id="item-34"></a>34 | **Neither capture engine taints its canvas. Cross-origin content the page may not read is left out of the capture instead.** HTML-in-canvas draws a cross-origin image only when it has `crossorigin` and a CORS response; any other cross-origin image, every cross-origin CSS background and every cross-origin iframe draws as transparent, and the canvas stays readable. snapDOM fetches each resource with CORS: a CORS image or CSS background draws, a non-CORS image becomes a gray placeholder, a non-CORS background draws nothing, and a cross-origin iframe becomes a placeholder. The two engines differ on a CORS CSS background: snapDOM draws it, HTML-in-canvas does not, because the page loads backgrounds without CORS. So a Surface needs no taint check, and its 3D copy shows a hole or a gray box where the page shows non-CORS content. (measured 2026-10-09, Chrome 155.0.8059.40 and Chrome for Testing 156.0.8078.5 and 157.0.8080.0 with `--enable-features=CanvasDrawElement`, snapDOM 3.0.0-beta.1; `npm run probe:capture-origin`; same pixels on 3.8.2) | 100x100 element per case, page on `127.0.0.1`, assets on `localhost`, center pixel after a repaint. HTML-in-canvas: same-origin and CORS image `255,0,0,255`; non-CORS image, non-CORS and CORS background, iframe `0,0,0,0`. snapDOM: same-origin and CORS image, CORS background `255,0,0,255`; non-CORS image `204,204,204,255` with an `image-fallback` warning; non-CORS background `0,0,0,0`; iframe `221,221,221,255`. `getImageData` succeeded on all 12 capture canvases on all three builds. A planted draw of a non-CORS image into the capture canvas made `getImageData` throw `SecurityError`, and the probe failed |
