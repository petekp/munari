# The platform, as measured: Safari and WebKit

This file holds what WebKit does differently, measured while bringing Safari onto the snapDOM engine. It is part of [the platform measurements](../platform.md), which lists every item and the table conventions.

| # | What the platform does | Evidence |
|---|------|---------|
| <a id="item-29"></a>29 | **WebKit answers three platform questions differently, and two of them throw rather than degrade.** Measured while bringing Safari onto the snapDOM engine. One: `Element.moveBefore` is absent (Chromium and Firefox 151 both have it), so a handoff there reparents with `insertBefore`, which loses focus, every scroll offset in the subtree, an iframe's document and a running CSS animation's progress — and nothing else; input values, canvas pixels, `<details>` state and listeners survive either way (decisions.md #61). Two: `getComputedStyle(el).overflowClipMargin` is **undefined**, not the empty string every other unsupported property returns, so reading the camelCase property and calling a string method on it throws; `getPropertyValue('overflow-clip-margin')` answers `''` everywhere. Three: `ResizeObserver.observe(el, {box: 'device-pixel-content-box'})` **throws** instead of ignoring the unknown box, taking down whatever mounted it. The shape of the lesson: an unimplemented CSS property degrades quietly and an unimplemented OPTION does not, so an option a browser may not know needs a `try`. (measured 2026-09-11, WebKit 26.5 via Playwright, dpr 2, snapDOM 3.0.0-beta.1) | `'moveBefore' in Element.prototype`: Chromium true, Firefox 151 true, WebKit false. Reparent survival, all three engines identical on `insertBefore`: value kept, canvas kept, `<details>` kept, listeners kept; focus lost, scroll 120 -> 0, iframe RELOADED, animation 434ms -> 0. Saving focus, selection and scroll around the move restores all three in every engine. Lab sweep in WebKit: 24/24 scenes load with zero page errors (23/24 before the ResizeObserver guard, 0/24 before the handoff change); Flight lifts, parks and lands with its typed value, focus and selection intact |
| <a id="item-30"></a>30 | **snapDOM's `toCanvas` resamples in WebKit; drawing its SVG yourself at the target size does not.** A Surface texture read visibly blurrier in Safari than in Chrome, and the cause was the exporter, not the capture. `toCanvas` returns a canvas of the asked-for size either way, but in WebKit that canvas carries a third less edge contrast than the same DOM — uniformly, a plain 1px border softening as much as the text, which is what says it is a SCALE and not a text-rendering difference. Reading the capture's own SVG (`toRaw()`, which is the serialized SVG on the default engine and costs nothing) into an `Image` and drawing it once at the target size is sharp, matches Chromium's raster exactly, and is CHEAPER. Nothing about the capture changes — same SVG, same styles, same fonts — so this is an exporter path to avoid, not a reason to avoid the engine. (measured 2026-09-11, WebKit 26.5 via Playwright and Chromium, dpr 2, snapDOM 3.0.0-beta.1) | Flight card 505x157 CSS at dpr 2, raster against that browser's own render of the element. WebKit via `toCanvas`: MAE 5.906, 26,273/317,140 px over 24 (8.28%), edge energy 0.652x the DOM's. Same card, same capture, drawn from `toRaw()`: MAE **4.003**, 12,097 px (3.81%). Chromium is MAE 0.000 by both routes. Per-band edge ratios before the change, WebKit: card border 0.809, rail 0.807, headline 0.766, body 0.738, divider 0.778, checkbox 0.744 — uniform. Median rasterize cost: WebKit 6 ms via `toCanvas` against 1 ms drawn directly; Chromium 1.7 ms against 1.6 ms |
| <a id="item-31"></a>31 | **Safari's frame loop has a ceiling the page cannot see, and snapDOM's WebKit font pass spends four of those frames per capture.** Safari 18.6 runs `requestAnimationFrame` at 30 fps while macOS Low Power Mode is on, and at 60 on a ProMotion display unless the "Prefer Page Rendering Updates near 60fps" feature flag is turned off; Chrome runs 120 in both states. So "Safari is half Chrome's frame rate" can be entirely the browser's ceiling, and a Safari number is only comparable to another Safari number taken in the same power state — record `pmset -g` beside every Safari measurement. What the ceiling then multiplies: snapDOM's font pass on WebKit awaits four animation frames per capture, 33 ms each at 30 fps, and re-derives and re-encodes every face each time. Supplying the same faces from a per-document cache and turning that pass off (decisions.md #62) removes the frames and the encoding with the same faces, the same payload and the same pixels. (measured 2026-09-12, Safari 18.6 and Chrome on a ProMotion MacBook Pro on battery, `powermode 1`, dpr 2, snapDOM 3.0.0-beta.1) | A plain page with no WebGL, same window size, same moment: Safari **29.9** fps, Chrome **119.9**. Lab scenes on snapDOM idle at 30 fps in Safari with zero captures; the same scene earlier that day on mains power ran at 59-60. Genie's bounce window, one capture: Safari 137 ms wall against Chrome 41 with snapDOM's font pass; with the faces supplied and the pass off, Safari **14** ms, five `@font-face` rules and 317 KB of payload either way, pixel output identical |
