# The platform, as measured: hit-testing and geometry of canvas children

This file holds how Chrome hit-tests a canvas's children, what a pose on the drawn root or the canvas costs, and how a drawn child's geometry reads. It is part of [the platform measurements](../platform.md), which lists every item and the table conventions.

| # | What the platform does | Evidence |
|---|------|---------|
| <a id="item-18"></a>18 | **Canvas children (`layoutsubtree`) are laid out and natively hit-testable, but never painted — and the hit region is CLIPPED to the canvas's CSS box.** Hit-testing follows CSS transforms including a full perspective matrix3d (browser does the w-divide); trusted clicks, focus, caret placement, typing, `:hover`, and drag selection all reach the child through a tilted pose. A child transformed outside its canvas's box stops being hittable there — the element under it wins. Holds at dpr 2, inside a same-origin iframe (the parent document hit-tests to the IFRAME and the browser routes through), and under page scroll: composition is standard CSS — child viewport position = canvas `getBoundingClientRect` origin + transform, for fixed and absolute canvases alike. (measured 2026-09-02, Chrome 151, dpr 1 and 2) | screenshots byte-identical with the child present vs `display:none` (a control div at the same spot changes them); trusted click → child button, `isTrusted: true`; typed into a transformed input, selected exact chars 0–11 by range-rect drag; in-box transform hits, out-of-box returns the page element — `docs/spikes/matrix3d-hit.md`; iframe/dpr/scroll: trusted click + `:hover` + live capture in a lab-shaped offset iframe at dpr 1 and 2; absolute canvas at doc (150,1000) at scrollY 800: predicted child origin [200,230] = measured — the addendum in the same report |
| <a id="item-19"></a>19 | **Browser hit-testing of a matrix3d child agrees with GL rasterization of the SAME MVP within ≤1.25px** (median 0.75px, edge scans at 0.25px steps, poses rotY/rotX 30°/12° and 55°/25°), unchanged at dpr 2, and the viewport·P·V·M·pixelToLocal recipe (three.js PR #31233) predicts the browser's own rects to 0.01px. (measured 2026-09-02, Chrome 151, dpr 1 and 2) | 24 edge scans, `elementFromPoint` flip vs `readPixels` flip: max 1.0px / 1.25px per pose; dpr 2 rerun of the steep pose: max 1.0px, median 0.75px; corner prediction vs `getBoundingClientRect`: [90.91,145.45,709.09,454.55] both |
| <a id="item-20"></a>20 | **Capture asymmetries of the drawn root:** a TRANSFORM on the root never enters the capture (bytes identical), but each transform RESTYLE on the root costs one paint — a per-frame transform paints every frame, on visible and hidden canvases alike (an earlier same-day run reported this paint-free from a single write; the denser count supersedes it); a STATIC root `opacity:0` is baked into the record — capture reads `[0,0,0,0]`, and stays blank across fresh records after mutations (item 4 covers *compositor-animated* root opacity only); canvas `visibility:hidden` with the child `visibility:visible` keeps paints firing and capture alive; canvas `opacity:0` keeps `onpaint` firing but blanks the capture. Consequence: an invisible hit-hosting canvas is possible via `visibility`, never via `opacity` — and a pose held by restyling the CHILD is a paint per frame (item 21 is the paint-free shape). (measured 2026-09-02, Chrome 151) | matrix3d'd root: capture byte-identical; root transform restyles: 30/30 paints under a canvas cover, 30/30 bare, 10/10 pre-capture, 10/10 post-capture, 10/10 on a visible canvas — `docs/spikes/cover-clip.md`; `opacity:0` root: `[0,0,0,0]` before and after a painted mutation; hidden-canvas rig: mutation paints, capture `[204,0,0,255]`; `opacity:0` canvas: mutation paints, capture `[0,0,0,0]` |
| <a id="item-21"></a>21 | **Native hit-testing clips to the canvas's TRANSFORMED box, and transform restyles on the CANVAS are paint-free after the first** — so the pose belongs on the canvas. The rig that follows: canvas CSS box = content box, canvas wears the full pose `matrix3d` from `transform-origin: 0 0`, child stays identity. The transformed box is then exactly the projected quad, so the hit clip is the content and nothing else — no cover geometry, no box growth, no density change (the CSS box never changes size, so item 8's replay ratio is untouched) — and holding or animating a pose costs 0 paints/frame while the capture stays alive underneath. (measured 2026-09-02, Chrome 151) | child quad fully outside the untransformed canvas box: unhittable bare, hittable when the canvas cover moves over it; perspective child under an affine cover agrees with predicted edges to 0.25px; canvas transform restyles: 0/10 translate, 0/30 full-perspective wobble, ~1 on first application; canvas-wears-pose run: centre hit + 0.25px edge agreement + trusted click, mutation under the worn pose captures correctly — `docs/spikes/cover-clip.md` |
| <a id="item-33"></a>33 | **Chrome 154–156 do not hit-test a canvas's children until the paint callback calls `canvas.updateElementGeometry(element)`. Chrome 153 and 157 hit-test them without it.** Without the call, `elementFromPoint` over the child returns the canvas, or whatever lies under a `pointer-events: none` canvas, and a real click reaches nothing. With it, the hit region is the child's layout box and follows later transforms of the canvas, as on 153. Chrome 157 also moves the child's box to where `drawElementImage` placed it; the engine draws at (0, 0), so the box does not move. Chrome 153 has no `updateElementGeometry`, so the engine calls it only where it exists. This is why `gate:lifting-pointer` and `gate:knobs-resize` failed on Chrome 154 locally and on the `ubuntu-24.04` runner image `20260927.320.1`, which moved from Chrome 153 to 154. (measured 2026-09-30, Chrome 154.0.8037.92 stable and Chrome for Testing 153.0.8010.52–157.0.8080.0, `--enable-features=CanvasDrawElement`) | a 120x60 button in a 300x200 canvas, page scanned every 10px with `elementFromPoint`: 72 hits on 153 and 157, 0 on 154/155/156, 72 on 154/155/156 with the call; after `translate(200px,100px) rotate(10deg)` on the canvas, the hits move with it (75). Hosted CI: `lifting-pointer` failed 5 of 5 attempts on image `20260927.320.1` and passed 6 of 6 on `20260920.314.1` |
| <a id="item-36"></a>36 | **On Chrome 157 and 158, a drawn canvas child's `getBoundingClientRect` can be one float32 step off its layout size. Its layout box is exact.** ResizeObserver's `borderBoxSize`, `offsetWidth`, computed `width` and the canvas's own rect stay exact. A check that compares a parked capture's size with a page element must read the layout box. (measured 2026-11-23, Chrome 158.0.8127.36 and Chrome for Testing 156.0.8078.47 and 157.0.8103.78, headless, dpr 1) | A 1000x100 `drawable` child in a `content="drawable"` canvas styled 1000x100, with no Munari code, read before and after one `drawElementImage` call at backing widths 1000, 2000, 2500, 3000, 3400 and 3600. On 157 and 158, only the 3400 case changes, to 999.9999389648438px, and only after the draw. That is 1000 minus 2^-14, the float32 value just below 1000. On 156, no case changes. `borderBoxSize`, `offsetWidth` and computed width read 1000 on every build. Plume's parked 1000px capture, drawn into a 3400px store, read the same value: `gate:plume` failed on CfT 157.0.8103.78 and stable 158.0.8127.36 and passed on CfT 156.0.8078.47 at the same commit. `instruments/plume/plainLayout.mjs` records this in its header and compares layout boxes |

**Items 18–21 support the opt-in native pointer route** (decisions.md #39 and
#42): for eligible planar poses, the parked canvas — `visibility:hidden`, lifted above the
renderer canvas, wearing the presenter's full matrix3d per item 21 —
hears trusted input natively on exactly the projected quad: hover,
focus, caret, selection, while its capture runs untouched and its
`:hover` self-paint draws the hover twin into the texture with no relay
code. Measured end-to-end in `docs/spikes/matrix3d-hit.md` and
`docs/spikes/cover-clip.md`. Deformed poses — fisheye, slider, crystal — use
relay, as do multiple interactive poses sharing one source. The binding also
checks input policy, inertness and geometry provenance. If HTML capture itself
is unavailable, a handoff Surface keeps its HTML native on the page. The three environment cases
were probed and cleared the same day (the matrix3d report's addendum):
the lab's iframe shell, dpr 2, and scrolled/offset canvases all behave;
only OS-level input needs iframe-offset coords — the kernel's own math
stays in its frame's space. `pointer/pointerRoute.ts` owns the
arbitration between the two routes.
